# Module 3 - LangGraph (상태 / 노드 / 그래프)

## 📅 2026-11-19 | TypedDict로 상태를 정의하고 그래프 만들기

> 코드: [`langgraph_basics.py`](./langgraph_basics.py)

### 개념

**1. LangGraph가 왜 필요한가**

- LCEL로 만든 체인은 `prompt | llm | output_parser`처럼 **한 방향으로 한 번 흐르고 끝남**. 되돌아가거나 조건에 따라 갈라질 수 없음
- 11월 16일에 `bind_tools`로 에이전트를 손으로 만들었을 때, 도구를 한 번만 부르고 끝나는 한계가 있었음. 검색 결과를 보고 또 검색해야 하는 질문은 처리하지 못했음
- LangGraph는 작업을 **노드(일을 하는 함수)** 와 **엣지(다음에 어디로 갈지)** 로 쪼개서 그림으로 그리듯 설계함. 그래서 반복과 분기를 표현할 수 있음
- `create_agent`가 내부에서 자동으로 돌려주던 ReAct 반복을, 이번에는 **설계도 수준에서 직접 그리는 것**임

**2. 상태(State)**

- 상태는 모든 노드가 함께 보고 고쳐 쓰는 **공용 작업판**임. 노드끼리 값을 직접 주고받지 않고, 상태를 통해서만 주고받음
- `TypedDict`를 상속해 어떤 키가 있고 각 값이 무슨 자료형인지 미리 적어둠
- 이번 실습의 상태는 두 칸임. `messages`(대화 기록)와 `tool_output`(도구 실행 결과 텍스트)
- `str | None`은 문자열이거나 비어 있을 수 있다는 뜻임. 도구를 아직 안 썼을 때는 값이 없기 때문

**3. TypedDict의 성격**

- 딕셔너리를 만드는 방식은 네 가지였음. `{}` 기호, `dict()` 함수, 클래스를 타입 힌트로 지정, 클래스를 함수처럼 호출
- 어느 방식으로 만들든 `type()`은 전부 `<class 'dict'>`로 나옴. **TypedDict는 새로운 자료형을 만드는 게 아니라, 평범한 딕셔너리에 설명을 붙이는 것**임
- 그래서 키 이름을 틀리게 써도 파이썬이 실행 중에 막아주지 않음. 편집기와 타입 검사 도구가 경고를 줄 뿐임

**4. Annotated와 리듀서**

- 노드가 `{"messages": [AIMessage(...)]}`를 반환하면, LangGraph는 그 값을 상태에 반영함
- 아무 표시 없이 `list[BaseMessage]`로만 두면 **새 리스트가 기존 리스트를 통째로 대체**함. `[HumanMessage]`가 `[AIMessage]`로 바뀌어 대화 기록이 사라짐
- `Annotated[list[BaseMessage], add_messages]`는 "이 칸을 덮어쓰지 말고 `add_messages` 함수가 시키는 대로 합쳐라"는 지시임
- `add_messages`는 기존 리스트와 새 리스트를 **이어붙임**. 그래서 대화가 누적됨
- 이렇게 "값을 어떻게 합칠지"를 정하는 함수를 리듀서라고 부름. `tool_output`에는 리듀서가 없어서 매번 덮어쓰기로 동작함

**5. 노드 함수의 규칙**

- 매개 변수 자료형을 `AgentState`로 지정하고, 입력으로 **상태 전체**를 받음
- 필요한 값은 `state["messages"]`처럼 키로 꺼내 씀
- 실행 결과를 **딕셔너리로 반환**하면 LangGraph가 상태에 반영함. 바꿀 칸만 넣으면 되고 나머지는 그대로 유지됨
- 반환 딕셔너리의 키는 **상태에 정의한 이름과 정확히 같아야 함**

**6. 그래프 구성과 실행**

- `StateGraph(AgentState)`로 그래프를 만들며, 어떤 상태를 쓸지 클래스로 알려줌
- `add_node("노드 이름", 실행할 함수)`로 노드를 등록함. 이름은 엣지를 연결할 때 쓰는 주소임
- `set_entry_point("노드 이름")`으로 시작점을, `add_edge("출발", "도착")`으로 연결을 지정함
- `END`는 LangGraph가 미리 만들어둔 종료 지점임
- `compile()`로 설계도를 실행 가능한 구조로 바꾸고, `invoke(초기 상태)`로 실행함. 결과는 **마지막 상태 전체**임

### 왜 이렇게 코딩했는가

- `call_tool`에서 도구 결과를 `messages`와 `tool_output` **두 군데에 넣은** 이유는 쓰임이 다르기 때문임. `messages`는 대화 기록이라 나중에 LLM에 통째로 보내는 용도이고, `tool_output`은 다음 노드가 바로 꺼내 쓰기 위한 자리임. `summarize_result`가 메시지 리스트를 뒤지지 않고 `state["tool_output"]` 한 줄로 값을 가져올 수 있음
- `call_llm`에서 `isinstance(messages[-1], HumanMessage)`로 확인하는 이유는, 두 번째 턴부터는 마지막 메시지가 `ToolMessage`나 `AIMessage`일 수 있기 때문임. 확인 없이 `content`를 꺼내면 엉뚱한 값을 사용자 질문으로 착각함
- `messages and ...`를 앞에 붙인 이유는 리스트가 비어 있을 때 `messages[-1]`이 에러를 내기 때문임. 파이썬은 `and` 앞이 거짓이면 뒤를 아예 실행하지 않음
- 노드 함수에서 LLM을 실제로 부르지 않고 `AIMessage`를 직접 만들어 반환한 이유는, 오늘의 목표가 **상태가 노드를 거치며 어떻게 바뀌는지 보는 것**이기 때문임. 진짜 LLM을 붙이면 응답이 매번 달라져서 흐름을 확인하기 어려움

### 막혔던 부분 · 이해 포인트

- **최종 상태에 AIMessage가 하나도 없었음**
  - 노드 세 개가 모두 실행됐다는 안내문은 출력됐는데, 최종 상태는 `[HumanMessage, ToolMessage]` 두 개뿐이었음
  - `최종 LLM 출력`으로 찍힌 것도 요약문이 아니라 `도구 실행 완료`, 즉 `ToolMessage`의 내용이었음
  - 원인은 `call_llm`과 `summarize_result`의 반환 키가 `"messages"`가 아니라 **`"message"`** 였던 것임. 상태에 없는 이름이라 LangGraph가 **에러 없이 무시**했음
  - `call_tool`만 `"messages"`로 제대로 써서, 그 노드가 만든 `ToolMessage`만 상태에 들어갔음
  - 노드는 분명히 실행됐고 에러도 없는데 결과만 사라진 상황이라, 출력 안내문만 보면 정상으로 보였음
  - 조용히 무시되는 함정이 이번 주에만 두 번째임. 11월 18일 `search_kwaargs` 오타도 같은 종류였고, 그 전에는 10월 20일 XGBoost가 모르는 매개변수를 무시한 것과 11월 10일 `tast` 오타가 있었음
  - 저장소에 올린 `.py`에서는 `"messages"`로 고쳤음. 위 출력은 수업 노트북 그대로의 결과임
- **TypedDict가 키 이름을 안 지켜줬음**
  - 방식3에서 클래스에는 `is_active`라고 적었는데 딕셔너리에는 `is_activate`라고 썼음에도 에러 없이 그대로 출력됐음
  - `type()`이 전부 `<class 'dict'>`인 걸 보고 이유를 알았음. TypedDict는 **실행 중에 검사하지 않음**
  - 그러니까 위의 `"message"` 오타도 TypedDict가 막아줄 수 있는 게 아니었음. 상태를 클래스로 정의했다고 해서 안전해지는 건 아니라는 뜻임
  - 이름을 맞추는 건 결국 내가 해야 하는 일이고, 편집기 경고를 보는 습관이 필요함
- **LCEL 체인과 그래프의 차이가 손에 잡혔음**
  - 체인은 `|`로 이어서 한 줄로 흐르고, 중간 결과를 꺼내 보려면 체인을 쪼개야 했음
  - 그래프는 노드마다 상태를 받고 상태를 돌려주는 구조라, 매 단계에서 무엇이 들어오고 나갔는지 `print`로 볼 수 있었음
  - 오늘은 일직선(`시작 -> LLM -> 도구 -> 요약 -> 끝`)이라 체인과 모양이 같았지만, 엣지를 되돌려 연결하면 반복이 된다는 것이 보였음
- **상태를 공용 작업판으로 보는 게 핵심이었음**
  - 11/16에 손으로 만든 에이전트에서는 `messages` 리스트를 while문 안에서 직접 `append`했음
  - 오늘은 각 노드가 "내가 바꿀 칸만 딕셔너리로 돌려주면" LangGraph가 알아서 반영했음
  - 노드끼리 서로를 모르고 상태만 아는 구조라, 노드를 추가하거나 순서를 바꾸기가 쉬워짐

## 📅 2026-11-20 | Pydantic BaseModel로 상태 정의하기

> 코드: [`langgraph_pydantic_state.py`](./langgraph_pydantic_state.py)

### 개념

**1. Pydantic BaseModel**

- `BaseModel`을 상속해 클래스를 만들면 **진짜 새로운 자료형**이 생김. `type()`이 `<class '__main__.User'>`로 나옴
- 어제 `TypedDict`로 만든 건 `type()`이 `<class 'dict'>`였음. 이름만 붙은 평범한 딕셔너리였던 것과 대비됨
- 값은 `user.id`처럼 **점(.)으로** 꺼냄. 딕셔너리처럼 `user["id"]`로는 못 꺼냄
- `model_dump()`를 쓰면 딕셔너리로 바꿀 수 있고, 그다음부터는 `.get("id")`로 접근함

**2. 유효성 검사**

- `BaseModel`의 핵심은 **객체를 만드는 순간 자료형을 검사**한다는 것임
- `name: str`로 선언한 자리에 리스트를 넣으면 `ValidationError`가 나면서 멈춤
- 같은 구조를 `TypedDict`로 만들어 똑같이 넣어보면 아무 일 없이 그대로 저장됨
- 그래서 외부에서 들어오는 값을 다룰 때, 잘못된 데이터가 **안쪽으로 흘러 들어가기 전에 막을 수 있음**

**3. Field()**

- `Field()`로 기본값과 설명을 함께 달 수 있음
- `default=None`은 그 값을 기본값으로 쓰라는 뜻
- `default_factory=list`는 객체를 만들 때마다 **새 빈 리스트를 만들어** 기본값으로 쓰라는 뜻. 리스트는 여러 객체가 같은 걸 공유하면 문제가 생기기 때문에 이렇게 씀
- `description`은 사람이 읽는 설명이고 동작에는 영향을 주지 않음

**4. 상태가 BaseModel이 되면 달라지는 것**

- 노드 함수에서 값을 꺼낼 때 `state["messages"]`가 아니라 `state.messages`로 접근함
- `Annotated[list[BaseMessage], add_messages]`는 그대로 씀. 리듀서는 상태를 무엇으로 정의하든 똑같이 동작함
- 초기 상태도 딕셔너리가 아니라 `AgentState(messages=[HumanMessage(...)])`처럼 객체로 만듦
- 노드 함수의 **반환값은 여전히 딕셔너리**임. LangGraph가 그 딕셔너리를 받아 상태 자료형으로 바꿔 반영함

**5. 조건부 분기 설계 (실습3, 진행 중)**

- 어제 만든 그래프는 `시작 → LLM → 도구 → 요약 → 끝` 일직선이라 **항상 도구를 썼음**
- 실제 에이전트는 질문에 따라 검색을 할지 말지 갈라져야 함. 그래서 상태에 `needs_search`(불리언)와 `search_results`(문자열) 칸을 추가함
- `classifier_node`는 LLM에게 `SEARCH` 또는 `NO_SEARCH` **한 단어만** 출력하게 시키고, 그 문자열을 `decision == "SEARCH"`로 불리언으로 바꿔 상태에 저장함
- `answer_node`는 `state.needs_search`와 `state.search_results`를 보고 시스템 프롬프트를 **다르게 조립**함. 검색을 거쳤으면 검색 결과를 프롬프트에 넣고, 아니면 일반 비서 지침만 줌
- 분기를 실제로 연결하는 라우팅 함수는 다음 시간에 이어서 함

### 왜 이렇게 코딩했는가

- 상태를 `TypedDict`에서 `BaseModel`로 바꾼 이유는, 에이전트가 커질수록 상태에 잘못된 값이 들어가는 사고를 막아야 하기 때문임. 어제 본 것처럼 `TypedDict`는 아무것도 막아주지 않음
- `messages`에 `default_factory=list`를 쓴 이유는, `default=[]`로 쓰면 그 리스트 하나를 모든 객체가 공유해서 한쪽에서 추가한 메시지가 다른 쪽에도 보이는 문제가 생기기 때문임
- `tool_output`을 `str | None`에 기본값 `None`으로 둔 이유는, 도구를 거치기 전에는 값이 없는 게 정상이기 때문임. 빈 문자열 `""`로 두면 "값이 없는 것"과 "도구가 빈 결과를 돌려준 것"을 구분할 수 없음
- 실습3에서 분류 결과를 문자열이 아니라 불리언으로 바꿔 저장하는 이유는, 나중에 라우팅 함수가 **True / False 두 갈래로만** 판단하면 되게 하기 위함임. `"SEARCH"`, `"search"`, `"SEARCH."` 같은 변형을 그때마다 비교하지 않아도 됨
- 분류 프롬프트에 "다른 설명은 일체 포함하지 마세요"까지 적은 이유는, LLM이 친절하게 이유를 덧붙이면 `decision == "SEARCH"` 비교가 바로 깨지기 때문임

### 막혔던 부분 · 이해 포인트

- **요약 AIMessage가 또 사라졌고, 이번엔 Pydantic도 못 막았음**
  - 어제와 같은 증상이 다시 나왔음. 노드 세 개가 모두 실행됐는데 최종 상태의 `messages`에는 `[HumanMessage, AIMessage("도구 사용을 요청합니다."), ToolMessage]`만 있고 **요약 AIMessage가 없음**
  - `최종 LLM 출력`도 요약문이 아니라 `도구 실행 완료`로 찍혔음
  - 원인은 어제와 똑같이 `summarize_result`의 반환 키가 `"message"`였던 것임. `call_llm`은 `"messages"`로 고쳐져서 이번엔 제대로 들어왔고, 요약 노드만 남아 있었음
  - **여기서 중요한 건, 상태를 Pydantic `BaseModel`로 바꿨는데도 이 오타를 못 잡았다는 것임**
  - 어제 나는 "`TypedDict`가 실행 중에 검사를 안 해서 못 잡았다"고 정리했는데, 오늘 결과를 보면 원인이 거기에 있는 게 아니었음
  - Pydantic이 검사하는 건 **상태 안에 들어갈 값의 자료형**이지, **노드가 반환한 딕셔너리의 키 이름**이 아님. 상태 스키마에 없는 키는 LangGraph가 반영 단계에서 그냥 무시함
  - 그러니까 상태를 무엇으로 정의하든 이 종류의 오타는 못 잡음. 유효성 검사가 지켜주는 범위가 어디까지인지가 눈에 들어왔음
- **`TypedDict`와 `BaseModel`의 차이를 에러 메시지로 확인했음**
  - `name: str` 자리에 `["수지"]`를 넣었을 때, `Customer`(TypedDict)는 `{'id': 1, 'name': ['수지'], ...}`로 그냥 저장됐음
  - `User`(BaseModel)는 `ValidationError: Input should be a valid string [type=string_type, input_value=['수지'], input_type=list]`로 멈췄음
  - 기대한 자료형, 실제로 들어온 값, 실제 자료형을 다 알려줘서 어디를 고쳐야 할지가 바로 보였음
  - 어제 `is_active`를 `is_activate`로 잘못 써도 통과했던 게 같은 이유였다는 게 연결됐음
- **입력은 객체인데 결과는 딕셔너리로 돌아왔음**
  - `AgentState(messages=[...])`로 객체를 만들어 `invoke()`에 넣었는데, `final_state`는 `{'messages': [...], 'tool_output': '도구 실행 완료'}` 형태의 딕셔너리였음
  - 그래서 결과를 꺼낼 때는 `final_state.messages`가 아니라 `final_state["messages"]`를 써야 했음
  - 노드 안에서는 점 접근, 결과에서는 대괄호 접근으로 **같은 상태인데 꺼내는 방법이 달랐음.** 헷갈리기 쉬운 지점이라 적어둠

## 📅 2026-11-23 | 조건부 분기와 에이전트 챗봇

> 코드: [`conditional_agent.py`](./conditional_agent.py)
> 코드: [`single_agent_chatbot.py`](./single_agent_chatbot.py)

### 개념

**1. 라우팅 함수**

- 노드 함수는 상태를 바꾸지만, 라우팅 함수는 **다음에 갈 노드의 이름을 문자열로 반환**함. 상태를 건드리지 않음
- `def route_by_search_need(state) -> str:` 처럼 반환 타입이 `dict`가 아니라 `str`인 것이 노드 함수와의 차이임
- 안에서는 상태 값을 읽어 `if state.needs_search:`로 갈림길을 정하기만 함
- 판단(분류 노드)과 이동(라우팅 함수)을 분리한 구조임. 분류는 LLM이 하고, 그 결과를 보고 길을 고르는 건 파이썬 코드가 함

**2. 조건부 엣지**

- `add_edge`는 "무조건 저기로"이고, `add_conditional_edges`는 "함수가 시키는 대로"임
- 인자가 세 개임. 출발 노드 이름, 라우팅 함수, 그리고 `{라우팅 함수의 반환값: 실제 노드 이름}` 대응표
- 대응표가 따로 있는 이유는 라우팅 함수가 돌려주는 값과 노드 이름이 꼭 같지 않아도 되기 때문임. `"예"` / `"아니오"`를 반환하게 하고 대응표에서 노드로 연결해도 됨
- 이번 실습은 둘을 같은 이름으로 맞춰서 대응표가 `{"search_node": "search_node", ...}` 모양이 됐음

**3. 두 경로 모두 검증하기**

- 일반 지식 질문(`파이썬에서 리스트와 튜플의 차이`)은 `NO_SEARCH` → 검색을 건너뛰고 바로 답변 노드로 갔음
- 최신 정보 질문(`Nvidia 2026년 2분기 영업 실적`)은 `SEARCH` → 검색 노드를 거쳐 답변 노드로 갔음
- 같은 그래프에 질문만 바꿔 넣었는데 실행 경로가 달라졌음. 11월 19일에 만든 일직선 그래프와 결정적으로 달라진 지점임
- 각 노드와 라우터가 `print`로 자기 이름을 찍게 해둬서, 출력만 봐도 어느 길로 갔는지 추적할 수 있었음

**4. 싱글 에이전트 — RAG 체인을 노드로 감싸기**

- 지금까지 만든 RAG 체인(`prompt | llm | output_parser`)을 그대로 두고, 검색과 체인 실행을 **노드 함수 하나 안에** 넣었음
- 그래프는 `rag_node` 하나에 `END`만 붙은 가장 단순한 모양임
- 즉 LangGraph를 쓴다고 해서 기존 체인을 버리는 게 아니라, **체인이 노드의 내용물이 되는** 구조임
- 상태도 `messages` 한 칸뿐임. 분기가 없으니 추가로 들고 다닐 값이 없음

**5. 멀티 에이전트 — 역할별로 나누기 (진행 중)**

- 싱글 에이전트는 노드 하나가 검색과 답변을 다 함. 멀티 에이전트는 역할별로 체인을 나누고 각자 잘하는 일만 시킴
- 첫 번째 역할은 **질문 재구성**임. `MessagesPlaceholder("chat_history")`로 대화 기록을 받아, 맥락에 기대는 모호한 질문을 혼자서도 이해되는 질문으로 바꿈
- 예: "그거 전액 다 받으려면 조건이 뭐야?" → "수강 신청한 강의를 전액 환불 받으려면 조건이 뭐야?"
- 프롬프트에 "질문에 답하지 말고, 오직 질문을 재구성하거나 그대로 반환하기만 하세요"라고 못 박음
- 그래프 구성은 다음 시간에 이어서 함

### 왜 이렇게 코딩했는가

- 분류 노드에서 `response.content.strip().upper()`로 앞뒤 공백을 지우고 대문자로 통일한 이유는, LLM이 `" search"`나 `"Search"`처럼 돌려줄 수 있기 때문임. `decision == "SEARCH"` 한 줄에 전부 걸려 있어서 비교 실패 가능성을 미리 줄인 것임
- 분류 결과를 문자열이 아니라 불리언으로 바꿔 상태에 저장한 이유는, 라우팅 함수가 `if state.needs_search:` 한 줄로 끝나게 하기 위함임. 문자열로 들고 다니면 갈림길마다 다시 비교해야 함
- `answer_node`가 `state.messages[-1].content`로 질문을 가져오는 게 두 경로에서 모두 통하는 이유는, 검색 노드가 `search_results`만 채우고 `messages`는 건드리지 않기 때문임. 그래서 검색을 거쳐 와도 마지막 메시지는 여전히 사용자 질문임
- 싱글 에이전트에서 `k=1`로 둔 이유는 FAQ가 한 행마다 완결된 질문-답변 쌍이라 하나만 가져와도 충분하기 때문임. 11월 17일 매뉴얼 실습과 같은 판단임
- `content_columns=["question", "answer"]`로 지정해 `faq_id`와 `category`를 뺀 이유는, 그 값들이 검색 대상 문장이 아니라 분류용 정보이기 때문임. 본문에 넣으면 `FAQ-001` 같은 글자가 임베딩에 섞여 들어감
- 벡터 저장소 폴더를 실습마다 `chroma_db_rag`, `chroma_db_multi`로 나눈 이유는, 같은 폴더를 쓰면 서로 다른 실습의 문서가 한 저장소에 섞이기 때문임

### 막혔던 부분 · 이해 포인트

- **단어 하나 뱉는 데 추론 토큰이 64개에서 256개까지 들었음**
  - 분류 노드는 `SEARCH` 또는 `NO_SEARCH` 한 단어만 출력하게 만든 노드임
  - 그런데 토큰 사용량을 보니 일반 지식 질문은 `completion_tokens` 75 중 `reasoning_tokens`가 64였고, 최신 정보 질문은 266 중 256이었음
  - 실제로 화면에 나온 텍스트는 각각 11토큰과 10토큰뿐이었음. 나머지 85%와 96%는 보이지 않는 추론 과정임
  - 어려운 판단일수록 추론이 늘어난다는 것도 보였음. 같은 분류 작업인데 Nvidia 질문 쪽이 4배를 썼음
  - 11월 12일 OpenAI API 실습에서 `reasoning_tokens`가 86.5%였던 것과 같은 현상임. 그때는 긴 답변이라 그러려니 했는데, **한 단어만 뽑는 작업에서도 똑같이 붙는다**는 게 확인됐음
  - 분기를 만들려고 넣은 분류 노드가 질문마다 이만큼을 쓴다는 뜻이라, 노드를 늘리면 비용도 같이 늘어난다는 걸 숫자로 보게 됐음
- **싱글 에이전트 챗봇은 이전 대화를 기억하지 못했음**
  - 상태에 `Annotated[list[BaseMessage], add_messages]`를 썼으니 대화가 쌓일 것 같았는데 그렇지 않았음
  - while 반복문 안에서 매 턴마다 `AgentState(messages=[HumanMessage(content=user_input)])`로 **초기 상태를 새로 만들고 있기 때문**임
  - `add_messages`는 한 번의 `invoke` 안에서 노드들이 메시지를 쌓을 때 작동하는 것이고, 턴과 턴 사이를 이어주지는 않음. 이어주려면 이전 `final_state`를 다음 턴의 입력으로 넘겨야 함
  - 그래서 "환불 정책이 뭐야?" 다음에 "그거 조건이 뭔데?"라고 물으면 '그거'가 무엇인지 알 수 없음
  - 멀티 에이전트 실습이 **질문 재구성 체인부터** 시작하는 이유가 여기서 보였음. 모호한 질문을 혼자 이해되는 질문으로 바꿔주는 역할이 먼저 필요한 것임
  - 11월 13일 LangChain 챗봇에서 `chat_history` 리스트에 직접 쌓았던 것과 비교됨. 그때는 리스트를 밖에 두고 계속 넘겼는데, 여기서는 매번 버리고 있었음
- **`load_dotenv`에 `override=True`가 붙었음**
  - 이전 실습에서는 `load_dotenv(".env")`만 썼는데 이번엔 `override=True`가 추가됐음
  - 기본값은 이미 설정된 환경 변수가 있으면 `.env` 값을 **무시**하는 것임. `override=True`를 주면 `.env` 값으로 덮어씀
  - 키를 바꿨는데 반영이 안 되는 상황을 막기 위한 설정으로 보임

## 📅 2026-11-24 | 멀티 에이전트와 비동기 처리

> 코드: [`multi_agent_chatbot.py`](./multi_agent_chatbot.py)

### 개념

**1. 멀티 에이전트 — 역할별로 나누기**

- 싱글 에이전트는 노드 하나가 검색과 답변을 다 했음. 멀티 에이전트는 역할마다 전용 체인을 만들고 각자 한 가지만 하게 함
- 이번 챗봇은 셋으로 나눴음. **질문 재구성** → **검색** → **답변 생성**
- 체인도 둘로 나뉨. `rephrase_chain`은 질문을 다듬고, `qa_chain`은 근거를 보고 답을 씀. 프롬프트가 서로 완전히 다름
- 역할을 나누면 한 프롬프트에 여러 지시를 욱여넣지 않아도 되고, 어느 단계가 잘못됐는지 출력으로 바로 짚을 수 있음

**2. 상태가 에이전트 사이의 통로**

- 에이전트끼리 직접 값을 주고받지 않음. 각자 상태의 자기 칸을 채우고, 다음 에이전트가 그 칸을 읽음
- `rephrase_node`는 `rephrased_query`를 채우고, `retriever_node`는 그걸 읽어 `context`를 채우고, `answer_node`는 둘 다 읽어 `messages`에 답을 넣음
- 상태에 칸이 세 개(`messages`, `rephrased_query`, `context`)인 이유가 여기서 나옴. 에이전트가 늘어난 만큼 주고받을 자리도 늘어난 것임

**3. 멀티턴 대화 만들기**

- 한 번의 `invoke`가 `END`에 닿으면 그 상태는 사라짐. 그래서 대화 기록을 `while` **바깥에** 두어야 함
- `inputs = {"messages": []}`를 반복문 밖에서 만들고, 매 턴 `inputs["messages"].append(HumanMessage(...))`로 질문을 덧붙임
- 실행이 끝나면 `inputs = final_state`로 최종 상태를 통째로 받아, 다음 턴의 입력으로 씀
- 턴이 쌓이면 `messages`가 `[HumanMessage]` → `[HumanMessage, AIMessage, HumanMessage]` → ... 로 늘어남

**4. 출력 파서를 붙이는 체인과 안 붙이는 체인**

- `rephrase_chain`에는 `StrOutputParser`를 붙였음. 결과를 검색어로 쓸 것이라 문자열이 필요하기 때문임
- `qa_chain`에는 붙이지 않았음. 결과가 `AIMessage` 그대로 나와서 `return {"messages": [response]}`로 상태에 바로 넣을 수 있음
- 즉 **그 결과를 어디에 쓸 것인지**가 파서를 붙일지 말지를 정함. 문자열이 필요하면 붙이고, 메시지로 쌓을 거면 떼는 것임

**5. 비동기 처리**

- 동기 방식은 한 줄이 끝나야 다음 줄로 감. LLM 응답을 기다리는 몇 초 동안 프로그램은 아무것도 못 함
- 비동기는 함수를 `async def`로 정의하고, 기다리는 지점에 `await`를 붙임. 기다리는 동안 다른 일을 할 수 있음
- LangChain은 같은 기능을 `invoke` / `ainvoke` 쌍으로 제공함. `await rephrase_chain.ainvoke({...})`처럼 씀
- 노드 함수도 `async def rephrase_node(state)`로 바꾸면 LangGraph가 알아서 비동기로 실행함. 그래프를 실행할 때도 `await agent.ainvoke(...)`를 씀
- 주피터 노트북은 이미 실행 환경이 준비되어 있어 `await main()`을 바로 쓸 수 있지만, `.py` 파일로 돌릴 때는 `asyncio.run(main())`으로 감싸야 함

### 왜 이렇게 코딩했는가

- `rephrase_node`에서 `if chat_history:`로 감싼 이유는, 첫 턴에는 이전 대화가 없어서 재구성할 것 자체가 없기 때문임. 조건 없이 매번 부르면 첫 질문에도 LLM 호출이 한 번 더 들어가 비용과 시간이 낭비됨
- `state.messages[-1]`과 `state.messages[:-1]`로 질문과 이전 기록을 나눈 이유는, 재구성 체인이 "이번 질문"과 "그 이전 맥락"을 구분해서 받아야 하기 때문임. 한 덩어리로 주면 무엇을 다시 쓸지 모름
- 검색 노드가 원본 질문이 아니라 `state.rephrased_query`로 검색하는 이유는, 재구성의 목적 자체가 **검색이 먹히는 질문을 만드는 것**이기 때문임. "그거 조건이 뭔데?"로는 아무것도 못 찾음
- 재구성 프롬프트에 "질문에 답하지 말고, 오직 질문을 재구성하거나 그대로 반환하기만 하세요"를 넣은 이유는, 이 지시가 없으면 LLM이 친절하게 답을 해버리기 때문임. 그러면 그 답변이 검색어로 들어감
- 답변 생성 체인에도 `MessagesPlaceholder("chat_history")`를 둔 이유는, 검색 결과만으로는 "아까 말한 그것"처럼 이어지는 말투에 자연스럽게 답할 수 없기 때문임. 재구성은 검색을 위한 것이고, 대화의 흐름은 답변 단계에서 따로 필요함

### 막혔던 부분 · 이해 포인트

- **멀티턴 대화의 해답은 `inputs`를 반복문 밖에 두는 것이었음**
  - 어제 싱글 에이전트 챗봇은 매 턴 `AgentState(messages=[HumanMessage(...)])`로 초기 상태를 새로 만들어서 이전 대화가 남지 않았음
  - 오늘 코드는 `inputs = {"messages": []}`를 `while` 바깥에 두고, 끝날 때 `inputs = final_state`로 받아 다음 턴에 넘김
  - 바꾼 줄은 사실상 두 줄뿐인데, `add_messages`가 **한 번의 `invoke` 안에서만** 작동한다는 걸 알고 나니 왜 밖에 둬야 하는지가 바로 이해됐음
  - 상태를 "노드끼리 주고받는 판"으로만 보다가, "턴과 턴 사이를 잇는 그릇"으로도 쓸 수 있다는 게 보였음
- **`qa_chain`에는 출력 파서를 안 붙였는데 그게 맞았음**
  - 11월 20일 실습에서 `AIMessage(content=response)`라고 썼다가 메시지 안에 메시지가 들어가는 문제가 있었음
  - 오늘은 `qa_chain`에 파서가 없어서 `response`가 이미 `AIMessage`임. 그래서 `return {"messages": [response]}`로 감싸지 않고 그대로 넣는 게 맞음
  - 파서를 붙였다면 문자열이 나왔을 테니 `AIMessage(content=response)`로 감싸야 했음. **체인 구성이 그다음 줄의 모양을 정한다**는 걸 두 경우를 비교하고 알았음
- **`Model=`로 대문자를 써서 모델 지정이 무시됐음**
  - 비동기 실습에서 `ChatOpenAI(Model="gpt-5-nano")`라고 썼는데 `UserWarning: Model is not default parameter. Model was transferred to model_kwargs.`가 떴음
  - 매개 변수 이름은 소문자 `model`임. 대문자로 쓰면 LangChain이 "모르는 설정"으로 보고 `model_kwargs`에 넣어버려서, 실제로는 기본 모델이 돌아감
  - 지난주 `search_kwaargs`, `message`, `max_result`와 같은 종류인데 **이번엔 경고라도 떴다**는 게 달랐음. 경고가 에러처럼 멈추지는 않으니 넘어가기 쉬움
  - 실행 로그 위쪽의 노란 경고 상자를 그냥 지나치지 말아야겠다고 생각했음
- **재구성이 실제로 작동하는 건 아직 못 봤음**
  - 실행 결과가 1턴뿐이라 `chat_history`가 비어 있었고, `if chat_history:`가 거짓이라 재구성 체인은 호출되지 않았음
  - 출력의 `재구성된 쿼리`도 원본 질문 그대로였음
  - "환불하고 싶어요" 다음에 "그거 조건이 뭔데?"까지 물어봐야 이 구조가 왜 필요한지 눈으로 확인할 수 있음
